# 控制安全与运行语义

## 文档状态

- 状态：Authoritative
- 适用对象：修改 `ControlGuard`、状态机、interlock、执行保护的开发者

## 1. 安全主张

控制侧当前最核心的工程主张是：

- 最终安全裁决保持在本地 C/C++ 主链
- 任何上游命令都是请求，不是直接执行权
- stale、导航异常、急停、解锁状态都必须在运行时主链里显式收口

## 2. 关键状态语义

产品视角上，系统会经历如下运行态：

- `Disconnected`
- `Connected`
- `SessionReady`
- `Disarmed`
- `Armed`
- `Manual`
- `Auto`
- `MotorTest`
- `Failsafe`
- `EstopLatched`
- `Fault`

但这些状态并不是由一个模块独占维护，而是分层收口：

- session 平面：`gateway/GcsSession`
- 安全平面：`ControlGuard`
- 控制模式平面：`ControllerManager`
- 执行保护平面：`orangepi_send` PWM 安全层

## 3. `ControlGuard` 的职责

`ControlGuard` 是当前控制仓的最终安全裁决点，负责：

- arm/disarm
- estop latch/clear
- stale 输入归零
- navigation gating
- failsafe 进入条件
- mode 切换前置条件
- MotorTest 安全边界

因此，其他模块不应偷偷复制这套判断。

## 4. 当前必须稳定的运行语义

### 4.1 输入 freshness

- 上游 intent 的 `stamp_ns/cmd_seq/ttl_ms` 必须真实保留
- 不允许通过重写时间戳“制造新鲜命令”
- stale 归零属于安全语义，不是 UI 行为

### 4.2 导航 gating

- `Manual` 可弱依赖导航
- `Auto` 必须显式依赖导航健康和状态语义
- stale/invalid/degraded/fault 的导航结果不能继续当闭环依据

### 4.3 estop 与 failsafe

- estop 必须立即零输出并锁存
- 解除 estop 需要显式 clear，且应满足中性条件
- stale、mode 拒绝、导航不可信等应能真实进入 failsafe，而不是只改显示状态

### 4.4 MotorTest

- 与正常控制输出互斥
- 只允许在受限振幅和时长下执行
- disarm/estop/fault 应立即打断

## 5. 执行侧安全层

真正落到 STM32 之前，还会经过 `orangepi_send` 的执行保护，包括：

- 限斜率
- 反向保护
- 回中
- 心跳超时保护
- 逻辑通道到物理通道映射

这层负责“怎么安全地下发”，但不负责“该不该下发”。

## 6. 调整这类语义时的硬约束

如果你准备动：

- mode 迁移规则
- stale 处理
- estop/failsafe 行为
- MotorTest 保护
- 执行侧 interlock

最低要求是：

1. 明确为什么必须动这个点
2. 只改一个核心小点
3. 同步更新本文和相关契约文档
4. 做最小回归，至少覆盖受影响测试或 smoke

没有这些闭环时，不应进入主链改动。
