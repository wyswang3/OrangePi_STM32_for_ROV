# 演进记录与边界约束

## 文档状态

- 状态：Authoritative
- 适用对象：决定控制仓后续升级路线或整理历史决策时的开发者

## 1. 当前演进结论

控制仓已经从“链路能跑”的原型态，进入“authority 边界、遥测、failsafe、控制器框架逐步收口”的工程阶段。

当前主线不是大改架构，而是继续稳住：

1. `ControlGuard`
2. `TelemetryFrameV2`
3. `NavView -> ControlGuard`
4. 执行侧 PWM 安全链
5. replay / fault / timeline 诊断能力

## 2. 已成为当前基线的阶段成果

### 2.1 V1 闭环收口

已经进入基线的内容包括：

- upstream intent 时间元数据真实保留
- stale manual 自动归零
- `Failsafe` 真实进入控制主循环
- `gcs_server` 消费运行态权威遥测，而不是 demo telemetry
- gateway session 关键并发访问加锁
- `MotorTest` 链路闭合

### 2.2 P0/P1 导航语义进入控制保护

已经进入基线的内容包括：

- `NavState -> NavView -> ControlGuard` 语义收口
- stale/invalid/degraded/fault 不再折叠成单一布尔
- `Auto` 显式依赖导航健康

### 2.3 P2 控制器框架起步

已经进入基线的内容包括：

- `ControllerManager` 显式注册控制器
- PID hold controller 框架落地
- telemetry 组装逻辑统一

## 3. 当前推荐升级顺序

1. 继续稳住 authority 主线，不先做大功能扩张。
2. 先补 replay、fault、timeline 和真实 bench 样本闭环。
3. 只在 reference 契约、切换语义和验证能力足够时，再推进更深层控制器。
4. ROS2 继续停留在 mirror/diagnostics/tooling 外围层。

## 4. 维护禁区

默认禁止：

- 把最终控制 authority 迁到 Python、ROS2 或 GCS
- 因为代码旧就整体重写控制仓
- 在没有样本和最小设计的情况下并行改多个核心模块
- 把系统级操作文档重新堆回本仓

## 5. 动核心主链前必须回答的问题

1. 为什么必须改这个点，而不是外围 helper、文档或诊断工具。
2. 为什么这轮只改这个点。
3. 影响的契约、消费者和日志有哪些。
4. 最小回归验证是什么。
5. 哪些风险这轮明确没动。

回答不清时，不应进入核心主链改动。
